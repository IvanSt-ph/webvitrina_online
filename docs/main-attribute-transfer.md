# Перенос характеристик в локальную webv3

Статус: подготовлен код; применение не разрешено и не выполнялось.

Независимый CLI `scripts/preview-main-attributes.php` не загружает Laravel,
не вызывает старый импортёр/преобразователь, не запускает observers, сессии или кеш.
Их существующие ограничения остаются неизменными. CLI читает `.env` без изменения,
отклоняет DB_URL, неожиданный host и любую БД кроме явно указанной `webv3`.
Проверяет фактическую БД на единственном PDO. Preview использует READ ONLY.

Утверждённый XLSX закреплён SHA-256 в коде; ожидаются 2101 строка и 78 «Цвет».
Fingerprint включает снимки семи таблиц (включая товары и архивные значения),
схему, фактическую идентичность подключения, строки XLSX и все операции.
Изменение любого из этих данных требует нового preview.

## План и ограничения

- Добавляются только отсутствующие цвета с утверждёнными HEX; старые ID сохраняются.
- Шесть существующих точных «Цвет» преобразуются без замены ID. Другие названия
  принудительно не преобразуются; №260 защищён от замены привязки.
- Определения переиспользуются по полному содержимому, палитры сравниваются как наборы ID.
- Привязки вне XLSX сохраняются. Заменяется attribute_id существующей привязки,
  её ID сохраняется. sort_order приводится к XLSX.
- Активные значения заменяемых определений переносятся только для соответствующей
  категории товара после проверки совместимости. Архивные значения не переносятся
  и не активируются. Текст старых точных «Цвет», включая историю, переводится в ID;
  исходный текст сохраняется в журнале. Все даты и архивные метаданные сохраняются.
- SQL DELETE, DDL и копирование таблиц отсутствуют. Новые ID выдаёт MySQL;
  отрицательные ссылки плана разрешаются после INSERT и никогда не записываются как ID.
- Дубликаты, неизвестные цвета, неверные HEX, несовместимые значения, несколько
  одноимённых определений категории и дубликаты активных значений блокируют весь план.

Офлайн-проверка по резервной копии от 14 ноября дала:
14 INSERT colors, 6 UPDATE attributes, 90 INSERT attribute_color,
185 INSERT attributes, 1457 INSERT attribute_category,
621 UPDATE attribute_category (503 замены и 118 изменений порядка),
10 UPDATE attribute_values (9 переносов и цвет №25).
648 дополнительных привязок сохраняются. Повторный план после моделирования — 0 операций.
Это проверка файла дампа, не подтверждение текущего состояния работающей БД.

## Перед будущим применением — только после отдельного разрешения

1. Проверить доступность существующего MySQL, фактическую БД и ограничения подключения.
   Остановить пользовательские изменения через сайт/очереди/другие CLI на время работ
   по отдельному согласованию. Не менять окружение и не запускать новые серверы.
   Подтверждение OFFLINE — обязанность оператора, не автоматическое отключение сайта.
2. Проверить SHA-256 существующего дампа:
   `storage/app/private/backups/webv3_before_colors_20261114_170731_b63f1d.sql`,
   `dd6b5e0eba2aa4ea13fa469dda3fb23681586cb3bbbc674b4119a1c76563b148`.
   Он проверен структурно, но его восстановление не тестировалось.
   Если после дампа есть новые данные, полное восстановление уничтожит их:
   заранее согласовать актуальный backup/recovery point; не создавать его автоматически.
3. Получить preview (сам по себе не создаёт журнал и не меняет кеш):
   `php scripts/preview-main-attributes.php --database=webv3 --preview`.
   Вывод содержит исходные значения: не публиковать и не сохранять в Git.
4. Рассмотреть полный список операций и новый fingerprint. Не считать офлайн-счётчики
   разрешением на изменившийся план. До применения проверить ACL каталога журнала
   `storage/app/private/main-attribute-transfer` (в Windows права 0700 не заменяют ACL).
5. После отдельного разрешения использовать тот же CLI с `--database=webv3`,
   `--apply=<проверенный fingerprint>`,
   `--confirm=APPLY-REVIEWED-ATTRIBUTES-TO-webv3-OFFLINE`, `--backup=<путь к дампу>`.
   Команда не запускается автоматически и не является частью deploy/hooks.
6. Применение требует InnoDB и отсутствия триггеров. В одной SERIALIZABLE-транзакции
   блокируются полные диапазоны семи таблиц, повторяется fingerprint, сохраняется
   prepared-журнал с SHA-256, проверкой чтения и fsync. Перед каждым DML проверяется
   идентичность PDO. Длительные блокировки допустимы только в согласованное окно.
7. До COMMIT сверяются все исходные поля строк с ожидаемыми изменениями, включая
   товары, даты и архив. Повторно рассчитываются все 2101 строки: операций должно быть 0.
   Сохраняются журнал проверенного состояния и карта новых ID, после COMMIT — receipt.
8. После успешного COMMIT выполняется адресная инвалидация на том же PDO:
   `cat.filters.{id}` для изменённых категорий и всех предков (включая ссылки на
   общие изменённые определения), затем ключ версии `reviews.public-cache-version`.
   Последний заставляет ReviewRatingCache отвергнуть прежние публичные записи товаров,
   related/recommendations. Кеш дерева и страниц категорий не содержит характеристик
   и не очищается. Глобального flush нет. Laravel-префикс вычисляется по `.env`.
   Допускается только database-store в таблице cache на том же соединении; другой
   store/connection или config-cache блокирует CLI до применения и требует проверки.
   Перед каждым удалением ключа проверяется фактическая идентичность PDO, открытая
   транзакция запрещена. Preview возвращает список ключей, но не удаляет их.
   Затем повторить read-only preview и UI-проверку.

   Ошибка очистки не означает rollback: результат содержит committed=true,
   cache.success=false, failed_keys и предупреждение; CLI завершится с кодом 2.
   Не открывать сайт и не повторять перенос. Для повторной адресной очистки после
   отдельного разрешения использовать MainAttributeCache::invalidate на проверенном
   PDO с перечнем failed_keys из receipt/вывода и той же проверенной конфигурацией.
   Если receipt не записан, список ключей также есть в prepared-журнале.

Каталог `storage/app/private/main-attribute-transfer` настроен отдельно:
наследование ACL отключено, FullControl только Ivan и SYSTEM. Другие каталоги не
изменены. Запуск для записи журнала требуется от Ivan, не от sandbox-учётной записи.
Каталог и содержимое игнорируются Git. Журнал содержит исходные данные товаров,
но не конфигурацию подключения, пароли, токены или таблицу users.

## Ошибки и восстановление

До COMMIT исключение приводит к rollback всей SQL-транзакции. Журнал остаётся как
след попытки; prepared/verified-before-commit не доказывают COMMIT. Пропуски AUTO_INCREMENT
после rollback нормальны. Тесты на mock PDO не заменяют проверку настоящего InnoDB.

Потеря соединения при COMMIT означает неопределённый результат. Не повторять применение
и не восстанавливать дамп автоматически: сравнить текущее состояние с before/after и
картой ID в журнале. Ошибка записи receipt после COMMIT явно сообщается как COMMITTED.

При необходимости восстановления сначала сохранить текущее состояние и журналы,
проверить SHA-256 дампа и отсутствие CREATE DATABASE/USE/внешних перенаправлений,
согласовать потерю изменений после времени backup. Восстанавливать только после
отдельного разрешения и проверки целевого подключения webv3 при остановленных записях.
Дамп содержит DROP/CREATE и данные: восстановление разрушительно, не часть rollback
и не выполняется этим кодом. После восстановления сверить все 46 таблиц и строки
с manifest, проверить значения/историю и кеши до открытия сайта.

## Проверки без БД

`php vendor/phpunit/phpunit/phpunit --do-not-cache-result tests/Unit/MainAttributePlanTest.php tests/Unit/MainAttributeTransferSafetyTest.php tests/Unit/MainAttributeCacheTest.php`

Тесты используют массивы, файлы и mock PDO, не устанавливают соединение MySQL.
Тест сбоя применения читает локальный одобренный backup и пропускается без него;
его prepared-журнал создаётся в уникальном temp-каталоге и удаляется тестом.
Проверка транзакций на настоящем MySQL, актуального preview, ACL и кешей остаётся
отдельным этапом. Сейчас запрещено запускать apply.
