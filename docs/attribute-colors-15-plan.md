# Единая палитра из 15 цветов — 2026-11-13

## Контракт и изменения

`ColorPalette::INITIAL` содержит Белый, Чёрный, Серый, Красный, Синий, Голубой, Зелёный, Жёлтый, Оранжевый, Розовый, Фиолетовый, Коричневый, Бежевый, Золотой, Серебристый.

Для точного имени `Цвет` импортёр проверяет полное совпадение выбранных ID с разрешёнными через справочник 15 названиями. Административное создание/редактирование требуют массив палитры и проверяют то же правило. Общий `AttributeDefinitionService` повторяет проверку внутри транзакционного пути под блокировкой справочника. Неполные, лишние и повторяющиеся ID запрещены; отсутствующие/неоднозначные названия справочника блокируют операцию. Порядок ID не важен. Нормализация названий: нижний регистр и `ё → е`.

Другие характеристики (`Цвет корпуса`, `Цвет свечения` и т. п.) не получают стандартную палитру принудительно. Преобразование старых определений использует обновлённый INITIAL и по-прежнему обновляет существующие ID без создания определений. Оно не вызывает обычное административное редактирование.

Готовый Excel `docs/templates/category-attributes-colors-2026-11-13.xlsx` обновлён только в 78 ячейках I с точным attribute_name=Цвет. Сохраняются 2101 строка, 9 столбцов, type=color, is_filterable=1 и порядок. Сравнение до/после проверило все остальные значения ячеек, включая 2023 нецветовые строки; другие части ZIP совпадают побайтно. Другие книги не изменялись.

## Предложение уникальности справочника (не реализовано)

Безопасный вариант — отдельный вычисляемый нормализованный ключ имени и UNIQUE по этому ключу. Выражение должно точно повторять правило приложения: замена ё на е после приведения регистра. Для ключа использовать бинарное сравнение, чтобы SQL collation не объединяла дополнительные буквы, которые приложение различает. При запрете пробелов по краям не добавлять скрытую нормализацию TRIM только на стороне БД.

Предпочтителен generated column, чтобы прямые SQL-записи не могли забыть заполнить ключ. Перед выбором окончательного DDL проверить поддержку выражения на MySQL 8.4, согласовать результат LOWER/REPLACE с PHP mb_strtolower на допустимых названиях, проверить Unicode и пробелы. Альтернатива — сохраняемый приложением ключ с UNIQUE, но без дополнительного механизма на стороне БД она не гарантирует защиту при обходе приложения.

Аналогично можно защитить HEX уникальным нормализованным ключом верхнего регистра и отдельно ограничить формат #RRGGBB. Существующую запись Синий #0011ff менять не нужно. Это отдельная будущая схема, а не миграция данного этапа.

Порядок будущей работы:

1. После отдельного разрешения снять резервную копию и выполнить read-only поиск коллизий по обоим будущим ключам, проверить все ссылающиеся ID.
2. Не объединять существующие строки автоматически: коллизии требуют отдельного рассмотренного плана с сохранением ссылок и истории.
3. Подготовить и проверить миграцию на отдельно разрешённой тестовой БД; учитывать блокировки DDL и отсутствие транзакционного отката многих DDL-операций MySQL.
4. Только после проверки данных и отдельного разрешения применить UNIQUE; приложение должно возвращать понятную ошибку при конкурирующей вставке.

Миграции не созданы и не выполнены. До появления ограничения БД ручная проверка уникальности требует исключить параллельные изменения справочника. Правила импортёра/сервиса не заменяют защиту от произвольного прямого SQL и старых сидеров.
