# PROD-05: остатки при отмене заказа

Checkout (`CheckoutController::create`) группирует корзину по продавцу:
одна корзина может содержать разных продавцов, каждый заказ — одного.
В общей DB transaction checkout блокирует товары через `lockForUpdate`, проверяет
доступность и количество, выполняет `decrement('stock', qty)` и сохраняет позиции
с денежными snapshot. Этот механизм не изменён.

## Жизненный цикл

- Статусы: `pending`, `processing`, `paid`, `shipped`, `delivered`, `completed`, `canceled`.
- Продавец: `pending → processing → paid → shipped → delivered → completed`;
  отмена из `pending`, `processing`, `paid`.
- Покупатель: запрос отмены до отправки (только причина и дата запроса);
  подтверждение получения из `shipped`/`delivered`.
- Администратор: любой бизнес-статус, включая отмену после отправки/завершения.
- `markAsPaid()` также делегирует изменение статуса в `Order::setStatus()`.
- Споры имеют отдельные статусы и не меняют статус заказа или stock.
  Состояний заказа `cancelled`, `rejected`, `refund` нет.

До PROD-05 `setStatus()` сохранял только статус/временную метку. Возврата stock,
транзакции изменения статуса и блокировки заказа не было.

## Гарантии

Все существующие пути смены статуса используют `Order::setStatus()`. Метод открывает
транзакцию, заново читает заказ с `FOR UPDATE`, проверяет конечное состояние и,
если переданы ограничения роли, допустимое исходное состояние. Проверка продавца
повторяется под блокировкой; устаревшая модель не позволяет отменить отправленный заказ.

Только переход в `canceled` возвращает количество каждой позиции. Позиции одного
товара суммируются; товары, включая soft-deleted, блокируются по возрастанию ID.
Обновление stock выполняется атомарным `increment`. Ошибка чтения/записи любого
товара или сохранения заказа откатывает весь возврат и статус. При deadlock
транзакция допускает до трёх попыток.

Повторный `canceled → canceled` ничего не меняет. Любой переход из `canceled`
в другой статус запрещён, включая административный, с ошибкой валидации.
Новая migration не нужна: конечный статус, сохранённый в той же транзакции,
служит признаком выполненного возврата. Денежные snapshot и удаление аккаунтов
не меняются; удаление аккаунта само по себе не возвращает остатки.

## Проверки

`OrderStockTest` покрывает реальный checkout, несколько позиций, seller/admin
отмену, запрос покупателя, повторный вызов, устаревшие модели, обычные статусы,
запрет восстановления, PROD-01, PROD-04 и rollback после второго SQL UPDATE.

`OrderStockConcurrencyTest` запускает два PHP-процесса с разными MySQL-соединениями.
Первый держит блокировку заказа, второй начинает отмену. Тест проверяет реальное
состояние `LOCK WAIT` в `information_schema.INNODB_TRX`, затем разрешает commit
первого процесса и проверяет, что stock увеличился только один раз.
Оба процесса используют защиту `Tests\TestCase` и только `webv3_testing`.

Дополнительный emergency-cleanup тест выбрасывает исключение в родителе, когда
первый worker держит блокировку, а второй находится в `LOCK WAIT`. В обоих сценариях
`finally` закрывает stdin и завершает процессы. Проверяются отсутствие их MySQL-сессий
и транзакций, отсутствие транзакции у родителя, неизменность config/env/рабочего каталога.
Механизм cleanup менять не потребовалось; добавлены проверки существующего поведения.

## Remaining risks

- В первоначальном прогоне было 377 passed, 1 failed: `PrivateBackupTest`, прежняя
  строка 53, `backup:run` вернул 1. Реальное сообщение команды тогда не сохранялось.
  Падение не повторилось ни в трёх комбинациях stock → backup, ни в двух последующих
  полных suite. Его точная причина неизвестна; это не объявляется исправленной
  regression или доказанным независимым flaky test. Связь с PROD-05 не подтверждена.

- Уже отменённые до исправления заказы не пересчитываются автоматически:
  статус/`canceled_at` не доказывают, выполнялась ли ручная корректировка stock.
  Нужна отдельная сверка исторических остатков, иначе возможен двойной возврат.
- Существующая административная отмена после отправки/завершения возвращает stock
  логически; подтверждение физического возврата и refund/payment не реализованы
  и не входят в PROD-05.
- Прямой SQL или будущий код, записывающий `orders.status` в обход `setStatus()`,
  обойдёт эти гарантии. Все найденные текущие пути используют метод.
- Уведомления и административный журнал по-прежнему выполняются после смены
  статуса отдельно. Их ошибка не отменяет уже зафиксированный возврат stock;
  повторная отмена безопасна для остатков, доставка уведомлений не exactly-once.
