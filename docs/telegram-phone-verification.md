# Подтверждение личного телефона через Telegram

## Границы

Подтверждается только личный `users.phone` продавца (`users.phone_verified_at`).
Покупателю телефон необязателен; Telegram endpoints для покупателей закрыты.
Регистрация создаёт аккаунт и магазин до подтверждения; черновики и настройка
магазина доступны по существующим правилам email. Публикация, в том числе через
администратора, и создание новых заказов требуют `User::canSell()`: роль seller,
подтверждённый email, непустой личный телефон и его подтверждение.
Проверки выполняются под блокировкой User в транзакциях публикации и checkout.
После смены телефона новые продажи блокируются, старые заказы остаются доступны
для исполнения и отмены. Существующие товары и статусы не переписываются.
Телефон магазина и его подтверждение независимы от личного номера.
Email Verification и password reset сохраняют прежние правила. Вход по телефону
и паролю требует подтверждённого телефона; Telegram удовлетворяет этому условию.
Форма входа принимает международный номер с `+` независимо от выбранной страны.
Для национального ввода страна выбирается явно (Молдова, Украина, Румыния,
Россия); список и правила находятся в существующем PhoneNormalizer. Например,
при выбранной Молдове `77111222` и `077111222` становятся `+37377111222`.
Без выбранной страны молдавский код не подставляется. Сохранённые номера не меняются.
Telegram подтверждает связь контакта с аккаунтом Telegram, а не текущий доступ к SIM.

## Подключение

Миграция `2026_11_07_000001_create_telegram_phone_verifications_table.php` должна
быть применена перед использованием обновлённого кода, включая изменение телефона
и удаление аккаунта. Дополнительно перед развёртыванием двухэтапного потока нужна
новая миграция `2026_11_21_000001_bind_telegram_phone_verifications_to_sessions.php`:
она добавляет `session_hash`, `contact_verified_at` и индекс пользователя/сессии.
Старые незавершённые заявки без привязки сессии больше не принимаются; продавец
создаёт новую. Уже подтверждённые номера и даты не изменяются.
Миграции и тесты в рамках этой работы НЕ запускались.

1. Создайте бота через BotFather. Используйте отдельного бота для тестирования.
2. Через управление секретами окружения задайте:

   | Переменная | Значение |
   | --- | --- |
   | `TELEGRAM_PHONE_VERIFICATION_ENABLED` | `true` |
   | `TELEGRAM_BOT_USERNAME` | username без `@` |
   | `TELEGRAM_BOT_TOKEN` | секрет BotFather |
   | `TELEGRAM_WEBHOOK_SECRET` | отдельный случайный секрет, например 64 hex-символа |

   SMS временно отключено в серверной конфигурации независимо от старого
   `TWILIO_VERIFY_ENABLED`: все четыре SMS endpoints возвращают 410 до вызова
   провайдера и записи статусов. Legacy-методы ProfileController также закрыты.
   Номера и прежние подтверждения пользователей и магазинов сохраняются.
   Возврат SMS требует отдельного изменения кода, а не изменения `.env`.
3. Обязательно обновите конфигурационный кеш принятым для проекта способом,
   иначе старое значение `services.twilio.enabled=true` может сохранить SMS.
   При использовании кеша маршрутов обновите и его: добавлен POST финализации.
   Для session blocking нужен общий для серверов cache store с поддержкой atomic locks;
   локальный `array` допустим только в тестах. Не используйте cookie session driver.
4. Вызовите Telegram `setWebhook` с параметрами:
   `url=https://YOUR_DOMAIN/telegram/webhook`, `secret_token=<webhook secret>`,
   `allowed_updates=["message"]`. Нужен публичный HTTPS с действительным сертификатом.
   Не вставляйте token в команды, историю терминала, тикеты или сообщения об ошибках.
   Используйте административный инструмент, получающий секрет из защищённой конфигурации.
5. Проверьте результат `getWebhookInfo`, не публикуя необработанный ответ.

Документация Telegram:
- https://core.telegram.org/bots/api#setwebhook
- https://core.telegram.org/bots/api#getupdates
- https://core.telegram.org/bots/features#deep-linking

## Сценарий и ограничения

Пользователь сохраняет личный номер с кодом страны. Кнопка Telegram создаёт
заявку и открывает бота в новой вкладке. Необходимо нажать Start и отправить
свой контакт кнопкой бота. В профиле кнопка «Проверить статус» получает текущее
состояние без раскрытия номера, токена и Telegram ID. Можно обновить страницу.
Этапы: «Ожидание Telegram» → «Контакт проверен» → «Завершить подтверждение».
Webhook сохраняет только `contact_verified_at`, но не `users.phone_verified_at`.
Последний устанавливается отдельным POST `/phone/telegram/finalize` из исходного
браузера после проверки CSRF, авторизации, подтверждённого email, роли продавца,
владельца заявки, привязки сессии, текущего номера, срока и отсутствия погашения.
Повторная финализация отклоняется без перезаписи даты подтверждения.

В заявке сохраняется HMAC-SHA-256 идентификатора сессии с ключом приложения
и отдельным контекстом `telegram-phone:`. Открытый ID сессии в заявку не записывается.
Другой браузер того же пользователя не получает ожидающую заявку через status
и не может завершить её по известному ID. Logout аннулирует незавершённые заявки
только исходной сессии перед её уничтожением. Создание, финализация и logout
используют session blocking; транзакции берут User перед заявками.
Истечение/смена сессии требует новой заявки. Смена APP_KEY также делает старые
привязки недействительными. Телефон магазина в этом потоке не изменяется.

Заявка живёт ровно 10 минут с момента создания (не с момента Start).
Один пользователь может создать не более трёх заявок за десять минут.
Создание новой аннулирует предыдущую, в том числе после смены A → B → A.
Один Telegram-отправитель может иметь только одну активную привязку.
Истёкшие привязки освобождаются при следующем подходящем событии.

Токен — 32 случайных байта в base64url, в таблице хранится только SHA-256.
Сырой токен передаётся только в redirect к Telegram, не сохраняется в session.
Заявка связывается с Telegram ID на первом Start и не может быть перепривязана.
Контакт обязан быть из личного чата, иметь `contact.user_id == from.id`,
совпадать с номером заявки и текущим номером пользователя. Проверяются также
возраст заявки, дата сообщения и строго более новые message_id/update_id,
чем у Start. Старый контакт не может подтвердить новую заявку.
После долгой задержки доставки Start может потребоваться отправить контакт заново.

Транзакции блокируют User перед заявкой. Смена номера использует существующий
PhoneAssignmentService и аннулирует заявки под той же блокировкой User.
Уникальные индексы защищают привязку Telegram ID и повторное использование событий.
Успешный повтор webhook не перезаписывает время подтверждения.
Существующее подтверждение через SMS также не перезаписывается Telegram.
Удаление аккаунта удаляет его заявки в транзакции анонимизации.

Webhook работает вне middleware web: без auth/session/CSRF, но с проверкой
`X-Telegram-Bot-Api-Secret-Token` и существующим CoordinateBackupWrites.
Тело запроса криптографически не подписано: доверие основано на HTTPS и secret.
Сетевые вызовы Telegram идут после транзакции. Сбой ответа бота не откатывает
проверку контакта: промежуточный статус доступен в исходном браузере, где всё ещё
необходимо выполнить финализацию. Срок не продлевается при проверке контакта.

## Локальные тесты без публичного сервера

Ниже команды для отдельного запуска пользователем после проверки кода и
подготовки **изолированной тестовой MySQL-БД**, разрешённой TestDatabaseSafety.
RefreshDatabase может изменять схему тестовой БД. Не используйте рабочую БД.
Новые тесты не включены в allowlist ExistingSchemaMode.

```powershell
php vendor/bin/phpunit tests/Feature/TelegramPhoneVerificationTest.php
php vendor/bin/phpunit tests/Feature/BuyerPhoneProfileTest.php tests/Feature/ShopPhoneProfileTest.php tests/Feature/PhoneVerificationRaceTest.php tests/Feature/PhoneUniquenessTest.php
php vendor/bin/phpunit tests/Feature/Auth/AuthenticationTest.php tests/Feature/Auth/EmailVerificationTest.php tests/Feature/AccountDeletionTest.php
```

Новый suite использует синтетические webhook POST, Http::fake и запрет
неподменённых HTTP-запросов. Реальный бот и публичный сервер не нужны.
Backup lock изолирован через tmpfile; cache/session/mail/logging изолированы.
В исходниках тестов предусмотрены владелец, secret, чужие и пересланные контакты,
текст, истечение, замена заявки, смена номера, удалённый пользователь, повторы,
ошибки Telegram, исходная/другая сессия, logout до и после контакта, CSRF,
обязательный email, атомарный откат финализации и сохранение прежней даты.
Браузерные JSON-запросы явно отправляют session cookie; webhook не отправляет её.
Обновлены положительные фикстуры CheckoutPickupWorkflowTest и
ProductMutationAuthorizationTest, а вход проверяется национальными и международными
форматами. Покупка без телефона покупателя предусмотрена в SellerPhoneAccessTest.
Наличие этих сценариев не означает их успешного выполнения: тесты не запускались.
Это регрессии порядка событий и устаревшего состояния; отдельный нагрузочный
тест с реальными параллельными MySQL-соединениями пока не добавлен.

Для ручной проверки настоящего бота без публичного сервера:
1. Используйте отдельного тестового бота без настроенного webhook.
2. Локальный доверенный polling-скрипт получает события через `getUpdates`
   с `allowed_updates=["message"]` и timeout 30.
3. Передаёт каждое событие POST на локальный `/telegram/webhook`, добавляя secret
   из защищённой конфигурации. Так проверяется именно рабочий HTTP-обработчик.
4. Продвигает offset до `update_id + 1` только после HTTP 200; при 503 повторяет
   событие с задержкой. Не выводит запросы, URL Bot API и ответы с контактами.
5. Пользователь создаёт заявку через локальный профиль, отправляет контакт,
   возвращается в исходный браузер и выполняет финализацию при подтверждённом email.

Polling-скрипт здесь не поставляется; для полностью автоматизированной локальной
проверки предназначены feature-тесты. Polling и webhook одного бота несовместимы.
Не отключайте webhook рабочего бота для локального эксперимента.

## Эксплуатационные риски

- До применения миграций обновлённые операции телефона, logout и удаления аккаунта
  работать не будут; требуется согласованное развёртывание кода и схемы.
- Не включайте запись тел webhook, заголовков secret, Location redirect и URL
  исходящего Bot API в reverse proxy/APM/Telescope/HTTP debug. Код не логирует
  эти данные, но внешняя инфраструктура может их перехватывать.
- Deep link является краткоживущим секретом. Не пересылайте его другим людям.
- Записи содержат персональные данные. Удаление аккаунта очищает их; отдельная
  периодическая очистка истории пока не добавлена. Перед эксплуатацией определите
  срок хранения и настройте очистку завершённых/истёкших записей, сохраняя минимум
  десятиминутную историю для лимита создания.
- Ошибки webhook возвращаются без деталей и без логирования входных данных.
  Мониторинг следует строить по HTTP-статусам, без записи содержимого запросов.
- При конкурентной попытке привязать один Telegram ID к разным аккаунтам
  уникальный индекс допускает только одну заявку; проигравший запрос может быть
  подтверждён HTTP 200 без сообщения бота. Повторите Start после завершения
  предыдущей заявки или истечения её срока.
- Реальные Telegram, MySQL-конкуренция, Blade и регрессионные тесты требуют
  отдельной runtime-проверки; php -l не заменяет её.
