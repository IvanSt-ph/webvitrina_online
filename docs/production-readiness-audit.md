Дата статической ревизии: 18 октября 2026 года, Europe/Chisinau. Проверенная
ревизия: `2d2e5da8c649fdb9412ed644e993d8a3af36747e`.

Это краткий актуальный статус, а не протокол успешного deployment. В рамках
ревизии читались исходники, конфигурационные шаблоны, Git и документация. Тесты,

но не выдается здесь за независимо проверенный факт.

Подробная историческая инвентаризация сохранена в
`docs/archive/production-readiness-audit-2026-10-17-detailed.md`. Её статусы и
номера строк относятся к более раннему коду.

## Вердикт

В проверенном коде не найдено подтверждённых P0/P1-дефектов основной цепочки
каталог → корзина → pickup-заказ → выдача. До безусловного production go-live
следует закрыть F06, устранить F08 либо временно отключить вложения чата и пройти
реальную инфраструктурную приёмку. F07 и F09 допустимо кратко отложить только с
операционными ограничениями, указанными ниже.

WebVitrina запускается как агрегатор с самовывозом. Онлайн-эквайринг и платёжные
webhooks не входят в текущий release gate.

## Оставшиеся задачи

### P0

Подтверждённых задач нет.

### P1 — обязательная инфраструктурная приёмка

1. Подтвердить production env: `APP_ENV=production`, `APP_DEBUG=false`, HTTPS,
   стабильный `APP_KEY`, secure/encrypted sessions, database queue и общий
   persistent database/Redis cache.
2. Подтвердить реальный worker, scheduler heartbeat, `failed_jobs = 0`, внешний
   `/up`, независимый запуск `production:health-check --json` и доставку тревог
   человеку. Один ручной healthy-ответ не подтверждает регулярный monitoring.
3. Проверить настоящие SMTP, verification/reset письма и уведомления заказов.
4. Создать backup v3, скопировать его вне основного сервера и выполнить isolated
   restore SQL, public files, private chat images и private review images. Проверить
   права backup-каталога и отсутствие HTTP-доступа.
5. Если существуют legacy public review images, выполнить dry-run, backup v3,
   перенос и подтверждённое удаление публичных копий по release runbook.

Это критерии приёмки, а не доказательство неправильной настройки текущего сервера:
фактическое production-окружение статически не исследовалось.

### P2 — дефекты F06–F09

- **F06:** перечитывать активного User под общей с удалением lifecycle-блокировкой;
  при отказе компенсировать созданные файлы. Закрыть до публичного запуска.
- **F07:** вынести инвариант последнего admin в общую сериализованную операцию.
  Временное ограничение — запретить self-delete и изменение роли admin до исправления
  и иметь проверенный recovery-доступ.
- **F08:** удалять загруженный chat image при провале INSERT и согласовать отправку
  с удалением conversation. Закрыть до запуска вложений либо временно отключить их.
- **F09:** удалить старый avatar только after commit, новый — при rollback/ошибке.
  До исправления не использовать замену avatar через admin user edit.

## Самостоятельные проверки

Если полный suite уже прошёл на этой ревизии и код с тех пор не менялся, повторный
прогон только ради документации не требуется. После исправления F06–F09 выполнить:

- гонка account delete с изменением имени, телефона и avatar;
- self-delete последнего admin и конкурентные demote/delete;
- ошибка INSERT после chat upload и удаление conversation между upload/INSERT;
- ошибка phone lock/User save после нового admin avatar;
- полный PHP suite после прицельных регрессий.

На staging вручную пройти регистрацию и verification, reset password, каталог,
корзину, полный pickup workflow с обоими подтверждениями, отмену и возврат stock,
чат, отзыв, проверку приватности изображений, worker/scheduler failure-recovery,
доставку тревоги и полный restore drill.

Точный порядок deployment и acceptance находится в `docs/release-runbook.md`.
