# WebVitrina: ключевые доменные инварианты

Этот документ описывает действующие контракты данных и границы восстановления.
Историю реализации и результаты прежних прогонов см. в `docs/archive/`; они не
заменяют проверку текущего кода и окружения.

## Заказы и расчёты

WebVitrina на текущем этапе поддерживает самовывоз. Checkout запрещает адрес
доставки и принимает только оплату наличными или картой продавцу при получении;
онлайн-эквайринга и платёжных webhooks нет.

Checkout резервирует одноразовый token в общем cache, перечитывает товары под
`lockForUpdate`, повторно проверяет продавца, доступность, цену и валюту и создаёт
заказы в общей DB-транзакции. Остаток уменьшается под той же блокировкой. Денежные
итоги проверяются в целых центах перед записью в ограниченные decimal-поля.

Pickup workflow разделяет два независимых факта: продавец подтверждает оплату,
покупатель — получение. Заказ завершается после обоих подтверждений. Переходы
статуса выполняются под блокировкой заказа. Отмена возвращает остаток однократно;
повторный запрос не должен увеличивать stock повторно. Прямые SQL-изменения статуса
обходят эти гарантии и не являются поддерживаемым способом работы.

## Неизменяемая история заказа

Заказ хранит снимки покупателя, продавца, магазина и контактов, а позиции — название,
SKU, изображение, цену, валюту и количество на момент покупки. История не должна
зависеть от последующего изменения или удаления профиля, магазина, товара либо
адресной книги.

Старые записи, заполненные backfill-миграциями, содержат данные, доступные на момент
миграции. Их нельзя трактовать как доказанно точное состояние на дату старого заказа.
History migrations с намеренно запрещённым `down()` не откатываются вслепую.

## Удаление аккаунта

`User::delete()` выполняет soft delete и анонимизацию в транзакции под блокировкой
User. Интерфейс восстановления удалённого аккаунта отсутствует; `forceDelete()`
запрещён. Заказы, позиции, денежные и контактные snapshots, события и споры
сохраняются. Новый аккаунт с тем же email или Google identity не наследует историю.

Удаляются активные credentials, sessions, remembered devices, reset tokens,
контакты профиля, адреса, корзина, избранное, подписки и связанные персональные
данные. Каталог удалённого продавца снимается с публикации; товары, участвующие в
заказах, сохраняются для истории. Файлы удаляются после commit; ошибки cleanup
логируются как требующие повторной обработки.

Известные ограничения текущего кода:

- **F06:** запрос, начавшийся до удаления, может сохранить имя, телефон или avatar
  обратно в уже анонимизированную soft-deleted строку. Writers должны перечитывать
  только активного User под общей lifecycle-блокировкой.
- **F07:** последний администратор может удалить себя через общий `/profile`.
  Инвариант «есть хотя бы один активный admin» должен находиться в общей
  сериализованной операции удаления/понижения роли.
- **F08:** вложение чата записывается до INSERT сообщения и при ошибке INSERT либо
  гонке с удалением диалога может остаться приватным orphan-файлом. Нужны
  компенсационная очистка и согласование send/delete.

## Файлы продуктов и пользовательские изображения

ProductService связывает DB-изменения с `ProductImageOperation`. Новые файлы имеют
уникальные имена и удаляются при rollback; старые удаляются только после commit.
Операция учитывает внешние транзакции, замены, gallery, soft delete и purge.
Исторические общие ссылки сохраняются до исчезновения последней активной ссылки.

Процессное завершение, отказ диска во время компенсации и прямое изменение путей
через SQL остаются за пределами транзакционного контракта. Сообщения
`Product image cleanup failed; retry required` и `Image upload cleanup failed;
retry required` требуют сверки DB-ссылок и ручного безопасного повтора.

**F09:** admin replacement avatar удаляет старый файл до успешного сохранения User.
Старый файл должен удаляться после commit, а новый — компенсироваться при ошибке.

Изображения отзывов и чатов хранятся приватно. Их HTTP-выдача должна проходить через
контроллер с проверкой участника/автора, статуса и связи файла с записью. Legacy
public review images переносятся по процедуре из release runbook.

## Публичный каталог

`NormalizeCatalogInput` ограничивает поддерживаемые query-параметры, типы строк,
идентификаторы, сортировки и пагинацию. Неизвестные ключи удаляются. Категорийные
атрибуты проверяются против filterable-набора текущей категории; количество ключей
и значений ограничено. SQL columns, relations и directions не берутся из запроса.

`page` ограничен диапазоном 1–10000, `per_page` — 1–100 для основного каталога.
Публичного catalog API, price-range filter и произвольного `limit` сейчас нет.
Category AJAX сохраняет существующее ограничение: он не реализует полный набор
search/sort/attribute filters. Числовые атрибуты всё ещё сравниваются через
существующее строковое поле `value`; это осознанная граница модели.

## Изменения этих контрактов

Новый writer файлов должен использовать общий `BackupWriteBarrier` вокруг DB-ссылок
и файловой мутации. Новый путь изменения заказа должен использовать существующий
workflow/service и блокировки. Прямые SQL, внешние writers, migrations и shell-
операции кооперативной блокировкой не защищены и требуют остановки writers по
release runbook.
