## Контракт импорта

Поддерживаются ровно два заголовка: прежний A:H и A:I с `colors` последним столбцом. В старом формате `colors` становится пустой строкой. Девятая ячейка данных при старом заголовке отклоняется.

Порядок: `category_slug, group_name, attribute_name, type, unit, is_filterable, options, sort_order, colors`.

`color`: `colors` — JSON-массив 1–100 названий (1–50 символов), `unit` и `options` пусты. Для остальных типов `colors` пустой. Нормализация названий цветов: нижний регистр и `ё → е`. Пробелы по краям, управляющие символы, дубли после нормализации, неизвестные и неоднозначные названия запрещены. JSON-объекты не принимаются вместо массивов. Цвета и HEX импорт не создаёт.

Определения сравниваются с учётом отсортированного набора ID цветов. `is_filterable=1` поддерживается. Точное название `Цвет` разрешено только с `color` в импортёре, общем сервисе создания определений и административной валидации. `Цвет корпуса` и `Цвет свечения` не затронуты. Это прикладное правило, не SQL CHECK: произвольные прямые SQL-записи его могут обойти.

Прежние конфликты блокируют весь импорт. Неправильный существующий тип не исправляется импортом. Совпадающий повтор даёт `UNCHANGED`, сохраняет прежний sort_order и не создаёт новых связей. Набор палитры участвует в signature, весь справочник и связи палитр — в fingerprint. Токен подтверждения версии 2; старое подтверждение требует нового preview. При apply справочник и связи перечитываются под блокировками. `webv3` явно запрещена guard даже при ошибочно разрешающей конфигурации.

## Отдельное преобразование

Команда `attributes:convert-colors` требует `--database=webv3_attributes_test`. Этот параметр НЕ переключает подключение: оно должно уже указывать на тестовую БД. Сервис проверяет фактическую БД через write-PDO до чтения таблиц и повторно внутри транзакции. Прямой вызов сервиса также защищён; другой движок или префикс таблиц запрещены.

Без `--apply` строится предварительный план с fingerprint. План требует все 15 цветов и включает исходные определения, связи, палитры, активные и архивные значения. Любое неизвестное, неоднозначное или выходящее за начальную палитру значение блокирует весь план. Числовой текст старого `text/select` не угадывается как ID. Текущее значение `color` проверяется как точный ID палитры.

Применение получает fingerprint повторного снимка под блокировками; несовпадение отменяет операцию. Обрабатываются только определения с точным бинарным названием `Цвет`. Все их ID сохраняются, связи категорий и sort_order не меняются. Тип становится `color`, unit/options — NULL, is_filterable — 1, палитра — 15 ID. Значения преобразуются в строковые ID с сохранением ID строки, product_id, attribute_id, timestamps, archived_at и archive_reason. Архив не активируется. Никакие определения и цвета не создаются. Повтор после успешного преобразования не меняет данные.

Перед первой SQL-записью создаётся уникальный JSON в `storage/app/private/attribute-color-conversion/`. Он содержит весь план и исходные значения; запись сбрасывается на диск, SHA-256 перечитывается и проверяется. Ошибка журнала блокирует SQL-изменения. Статус журнала `prepared` означает наличие исходного снимка, НЕ подтверждение commit: при SQL-ошибке/аварии журнал может остаться, а БД — откатиться. После успешного commit команда выводит путь и SHA-256. Проверка состояния БД обязательна; восстановление автоматически не запускается.

После commit команда очищает фильтры категорий и версию кеша каталога. Ошибка очистки отдельно сообщает, что данные сохранены. Перед применением также выполняется guard SQL-подключений моделей, кеша и сессий. Вызов сервиса напрямую не выполняет очистку кеша — рабочий интерфейс применения команда.
